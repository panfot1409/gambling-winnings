## 3. Path decision (directive: bot-branch layer “if minimal”, else dedicated branch)

The required layer is **not minimal**: it adds an acceptance-record schema, a chained
acceptance registry, legality-rule migration inside M3F, V2AB enumeration migration, an
independent stdlib reimplementation, registry-rebuild derivation, dashboard
accepted-state reporting, and a broad mutation-test matrix. Placing that on the bot
branch would conflate immutable proposal *evidence* with acceptance *machinery*.
Therefore: the **dedicated-branch path** —

1. PR #22 and its bot branch remain untouched, immutable proposal evidence.
2. This branch merges the exact bot head `779df6bb` with a **true merge commit**
   (commit 2), then layers acceptance artifacts and verifier migrations on top.
3. When this branch later merges to main, `779df6bb` becomes an ancestor of main and
   GitHub marks PR #22 merged; its branch is never rewritten or deleted.

## 4. Forward-only invariants (hard constraints, tested)

- The existing cohort verifier is never weakened; every current exact check either
  still holds byte-exact or is justified by an explicit acceptance record binding
  `old sha256 → new sha256` for that exact path.
- No vague “anything newer is fine” rule anywhere; production expectation is always a
  single exact state: `base ⊕ ordered acceptance chain`.
- No acquisition receipt, raw response, proposal file, or bot commit is edited — the
  acceptance layer only **adds** files.
- Proposed rows are treated as accepted **only** through the acceptance record; a
  production proposal present in the tree **without** a covering acceptance record
  remains illegal (the exact condition that made the five checks red stays enforced
  for any future unaccepted proposal).
- A future proposal can never silently rewrite old rows: append-only proofs
  (`require_exact_prefix` for chains; canonical-row prefix identity for the cohort)
  are re-verified at every acceptance, and acceptance N+1 must chain from the exact
  accepted state of acceptance N.
- Deleting, reordering, duplicating, or editing an acceptance record breaks the hash
  chain and fails closed everywhere (package verifiers, stdlib verifier, CI).

## 6. Verifier migrations (per surface; historical mode preserved everywhere)

- `eth_research.m3e.acceptance` (new module) — canonical strict reader/verifier:
  chain walk, artifact re-verification (every binding recomputed from committed
  evidence, nothing trusted), production expected-state resolution
  (`base ⊕ chain`), and the single legality predicate used everywhere:
  *production proposal legal ⟺ valid V2D anchor ∧ proposal bound by a valid
  acceptance record ∧ working-tree cohort equals the chain head's accepted state.*
- `eth_research.m3f.growable` — extended with acceptance-chain awareness via its own
  strict internal reader (M3F stays isolated: no import from m3e); the lattice's
  “delegated current state” gains the exact chain-head pin; `02_governance_state_legal`,
  honest-state derivation (`m3d_cohort_row_count`, `m3e_active`,
  `m3e_production_proposal_count`), `m3e_registry_chain` oracle, recovery capsule
  manifest expectation, and the recovery drill all consume it. Historical checks
  (`_verify_git_provenance`, frozen bytes at the recorded acceptance commit) are
  untouched.
- `tools/m3f_independent_verify.py` — independent stdlib chain-walk reimplementation
  (no shared code with the package readers, as designed).
- `eth_research.v2ab.freeze_table` — under (valid anchor ∧ valid chain): growable new
  paths excluded from “unlisted” enumeration exactly like the doc-table test already
  does; the six mutated entries verify against the chain-resolved expected hash;
  everything else stays byte-exact. The committed
  `research/v2ab/stack_freeze_table.json` bytes never change.
- `eth_research.m3e.registry.build_registry_bytes` — extended to derive
  production-proposal entries deterministically from committed proposal bundles
  (manifest self-hash, branch, idempotency key, previous-line hash), so
  “deterministic and matches committed” remains a full-rebuild test.
- Tests: literal pre-proposal pins are re-derived from the committed accepted state
  (never tautologically from the file under test — e.g. the m3d firewall test asserts
  `remaining_rows == 365 − accepted_row_count` **and** cross-checks

  acceptance event in the timeline.
- New mutation matrix (fail-closed proofs): drop/reorder/duplicate/edit a chain line;
